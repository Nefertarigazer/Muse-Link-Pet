# Rules

## 1 Operating rules (agents that operate the computer)

| ID | Rule | Why | How it is done |
| --- | --- | --- | --- |
| O1 | Check experience before acting; record and give feedback once the result is clear. | 2026-11-01 the user decided to accumulate methods from real tasks; 2026-11-13 the experience library shipped. | Look up the current app with `exp_lookup`, and give feedback with `exp_feedback` after use; draft, review and confirm a new method with `exp_record`. |
| O2 | Code and semantic interfaces first, then UIA, batches and screenshots as the application's exposure requires; do not guess at an ambiguous target. | 2026-11-02 the user decided semantics come first; 2026-11-08 a same-name button test confirmed the uniqueness gate; 2026-11-14 the user decided to record per application which tool works well and to look it up before acting. | First look up the application's experience tagged tool-choice and pick the tool from it; without one, observe/resolve and choose the action by role; add a scope or an explicit index for duplicate names; use a fresh screenshot when the current tree cannot express the target. |
| O3 | Report success, failure and uncertainty separately; when the outcome of input is unclear, check the current state first. | 2026-11-12 a review found an unverified delivery had been promoted to verified; when a wait disconnects, the target may still be executing. | Keep unknown and effect; prove the result by reading back on the target machine, or from the UI, logs or a hash; sending is proven by the message appearing in the conversation. |
| O4 | Clarify when a person, account, profile or object reference is unclear; verify identity for any action taken in a signed-in session. | 2026-11-01 an account reference was misheard; 2026-11-02 a web model tier fell back on its own. | Read the configuration and the page identity, tier and page state on the target machine; do not carry over conclusions from the development machine or from an earlier round. |
| O5 | Clipboard work has a backup, a source check and a restore; guards are in place before input. | 2026-11-01 clipboard prototype tests; 2026-11-08 a race between a user copy and an automatic paste. | Save the original content in a restorable form in the desktop session and confirm the source before pasting; restore only when the user has not replaced it with new content, and leave formats that cannot be saved completely to the user. |
| O6 | Once "Enter sends" is confirmed, input and send run back to back, and verification comes after. | 2026-11-02 the user settled that typing and the terminating key are one batch, and preparing a guard in between had delayed the send. | Check the content and the send key while preparing; follow the typing immediately with the terminating key, then check the conversation or task state; treat an unclear result as in O3. |
| O7 | Background tasks leave no console window; long tasks detach from the short SSH session and keep logs, a deadline and liveness evidence. | 2026-11-01 a daemon inherited a pipe and blocked the channel, and a relative script path failed to start. | Use a scheduled task through the launcher with absolute script paths; after starting, check the process and the listener; collect results with short requests. |
| O8 | One card at a time; authorization follows the actual options and the identity policy, and request text does not raise privileges. | 2026-11-12 the user settled that red lines and unknown types can only be asked or rejected; 2026-11-13 a busy card slot made an enrollment count as a failure. | Raise cards through the standard entrance and do not edit pending by hand; wait while the slot is busy; send privileged actions through authorize; the desktop pet's generic check does not act as an authorization option. |
| O9 | Keep the request ID after a wait times out and check the lifecycle first; report with fresh evidence. | 2026-11-12 17 requests were found with only their ACKs read; 2026-11-02 a blind text pipe still reported that generation had not finished. | Collect again with `muse-call -Check`; judge delivery by where the final reply sits; if generation flatlines for more than 3 minutes, switch to independent visual verification; align time zones before comparing clocks across machines. |
| O10 | Handle ACLs separately for directories and files; after restarting the host, verify zero listeners before verifying a single listener. | 2026-11-08 a directory inheritance parameter applied to a file produced zero ACEs; two hosts split traffic at random. | Use the owner repair and restart scripts, with a backup first; read back the file SDDL and Access.Count; after one start, check the version and exactly one listener. |
| O11 | Acceptance runs and one-off scripts call the entry points in the deployed directory, never the repository copy. | 2026-11-14 in run 5.5 two re-enrollment scripts called the muse-call in the repository, whose identity directory is anchored under the repository, so every reply was quarantined. | Scripts use the absolute path of the entry under the tool directory (site `pc_tool_dir`); afterwards check that no process command line contains a repository directory; the repository copy runs only in a test directory per E1. |
| O12 | Browser control prefers the official Muse browser extension; when it is absent, ask whether it may be added. | 2026-11-14 the user chose the official channel first, with the package-side browser stack only as a fallback. | If installed, verify it and use it without reinstalling; if absent, ask with one card (add it / do not add / cannot add); consent uses the official channel, and only a refusal or a failed installation uses the package-side stack, with the reason stated; no answer, closing or expiry is not consent. Workflow: operating guide section 3, Chrome. |


## 2 Engineering rules (people and agents changing this project)

| ID | Rule | Why | How it is done |
| --- | --- | --- | --- |
| E1 | Development does not touch production. | 2026-11-13 this round separated development from production. | Change files only in the designated worktree; test in temporary directories and on alternate ports; deploy the reviewed release package separately. |
| E2 | Every commit's file tree is publishable at any time. | 2026-11-13 the user decided private use and open source share one version. | Run `tools/check-public.py --patterns <private word list>` before committing and get 0; exclusions cover only transitional files that meet their deletion condition. |
| E3 | Private originals live outside the repository, which keeps only public templates. | 2026-11-13 the user designated a long-term private folder. | Store, map and install them per the private README; `private/` is ignored, and keys and run state are not committed. |
| E4 | Address values are looked up and filled in on the target machine during installation; if a value cannot be found, leave it empty with a note. | 2026-11-13 the user forbade substituting values from the development machine or the author's machine. | Templates stay empty and include the lookup method; the fields are in install section 2; for an existing installation read the current configuration instead of guessing common paths. |
| E5 | A new Windows installation defaults to a non-system local fixed disk; the system drive needs explicit permission. | 2026-11-13 the user decided tools and data should not occupy the system drive by default. | List drive letters and free space; creating a tool directory on the system drive requires `-AllowSystemDrive`. Windows OpenSSH, task registration and shortcuts are exceptions; venv, logs, the mailbox, experiences and the download cache follow the tool directory, and pip disables its cache. The agent-desktop state directory sits on a non-system disk outside the user profile (install section 4, step 1). Not applicable to the Linux VM. |
| E6 | Skip if already installed, do not move an existing installation, and add only missing items and differences. | 2026-11-13 the user required that nothing already installed be installed again. | Decide by existence, source and dependency hashes, content or task definition; the preview lists skip/new/change; force a redo with `-Force` / `--force`. |
| E7 | One site configuration; generated files are not edited by hand. | 2026-11-13 five templates were merged to prevent drift between the two sides. | Preview after changing the site configuration; leave matching files alone, replace differences through ReplaceConfig and keep the old files; see install section 2. |
| E8 | Both sides' release packages are exported from one commit. | 2026-11-13 the repackaging plan found a production fix that did not match the repository. | make-release builds the package with git archive; each side verifies the manifest, and acceptance is tied to the commit ID in RELEASE.txt; do not assemble a package from the working tree. |
| E9 | A retired protocol name is accepted only at the entrance, and new output uses the current name. | 2026-11-13 the release type moved to a generic name. | The old-name normalization sits in RETIRED_TYPES and the corresponding entrance; policy and business logic use the current name; the compatibility mechanism is in protocol section 2. |
| E10 | Line endings follow `.gitattributes`, and encoding follows the syntax check. | 2026-11-12 line endings and Windows PowerShell encoding affected execution. | bash/Python/JSON/MD use LF; CMD uses ASCII and CRLF; PS1 uses CRLF, with a UTF-8 BOM when it is not ASCII; run check-syntax. |
| E11 | Application experience goes into JSON through `exp record`, not into Markdown. | 2026-11-13 the user drew the line between the experience library and the documentation. | The schema validates it; public and local entries are kept apart; cross-application methods live in the operating guide and rules live in this file. |
| E12 | Incident postmortems go into the lessons table, and explanations are rewritten against the final code. | 2026-11-13 the user asked to remove process documents and duplicated facts. | Record the date, the symptom, the rule and the ID; write what is now fixed as the current mechanism; put anything you cannot judge in the delivery report. |
| E13 | A new document pair is justified in this file. | 2026-11-16 the user added CONTRIBUTING for open-source readiness, bringing public documentation to 13 Chinese-English pairs. | README covers the entrance, CONTRIBUTING the contributor workflow/checks/redaction/DCO, SECURITY the gates, RULES the rules, CHANGELOG the milestones; install, architecture, protocol, operating-guide and troubleshooting cover deployment, mechanism, contract, method and diagnosis; the plugin GUIDE and the bridge PROTOCOL are runtime entry points; standing-orders is the public template for private authorization. Adding a pair requires explaining why the existing files cannot hold the content. |
| E14 | UI text comes only from language packs, and documents are maintained in Chinese-English pairs. | 2026-11-13 the user settled the language pack and document pairing mechanism. | New UI text goes into en, zh-Hans and zh-Hant together; a card answer is mapped back to its key by the text rendered on that card, and a resumable card saves the rendered text; documents are paired with matching section numbers and change in the same commit; run check-i18n and check-docs. |
| E15 | Code is Apache-2.0, public experience entries are CC0 1.0, and the Muse name and artwork are outside the licenses; external contributions follow DCO 1.1. | 2026-11-13: the user chose the open-source licenses. | `LICENSE`, `NOTICE` and `library/LICENSE` hold the license texts and are not rewritten; the share card and the contribution note state CC0; no artwork bound by third-party rights is committed; external commits carry `Signed-off-by` (`git commit -s`). |

## 4 How to add a rule

First decide whether it is a rule, an application method or a mechanism description. A rule gets a stable ID in section 1 or 2 and fills in all of "rule / why (date and source) / how it is done"; an incident adds a row to the lessons table. Application methods go into experience JSON; mechanisms go into the file that already owns them. When changing an old rule, update the original entry and link the ID from the call sites.
